Jailbreak search

BOA (arXiv:2506.17299) asks whether any likely response of a model to a harmful request is a jailbreak. It searches the responses token by token, keeps only continuations whose probability stays above a threshold, scores a node by sampling lookaheads from it and sending them to a judge, and always extends the best-scored node next.

On Banyan the probability threshold is a pruning rule on the GPU, the lookaheads are samples in the same tree, and judge calls are batched. Here both sides search the same request with the same model, settings and judge.

What each side did in the first 200 seconds

A search node is scored from ten lookaheads that pass through it, each up to 200 tokens, through the same four-layer judge on both sides, and lookaheads already judged for a node above it count, as in the authors' code. So a node deep on a path that was already explored can be scored without a new lookahead; most of Banyan's scored nodes are scored this way, which is why it scores more nodes than it sends lookaheads to the judge.

Why 200 seconds: later in a run the authors' code can spend most of its time not searching. When a lookahead gets the judge's top score at its third layer, the response goes to the fourth layer (gpt-4o), and the search waits for that call; in the run shown it waited s within the first 200 s, and 413 s of the whole 671 s. In two other runs of the authors' code on this request, the search stopped adding any new text to its tree after about 250 and 360 s. The first 200 seconds compare the two searches while both are searching. One run per side.

What changed on 2026-11-23: Banyan picked the next node to extend whenever a slot was free, before the judge had scored the children it had already picked, and those children were judged first come, first served. A high-scored node's children then waited behind hundreds of low-scored ones, and in 600 s the search got 24 tokens deep with a best score of 0.42. Now Banyan does not pick while every judging slot is taken, so each pick is made with the scores of that moment.

A correction: until 2026-11-23 this site said Banyan scores 21 times as many nodes (97,636 against 4,641) in 600 s. Both counts were wrong for a comparison: ours counted lookaheads sent to the judge, not scored nodes, and the authors' run it compared with had stopped searching part way.

Setup

How this was measured

the authors' code
BOA's own search, through our evaluation's runner (its warm-up, seed and judge), with wrappers that note when every tree node is made, cut and scored, and every judge call. Their algorithm is not changed.
Banyan
The algorithm is our application on the user API. The measurement notes the time each node of the tree was made (the runtime's own new-node callback), wraps the application's own @judge to note each score, and notes when each node was picked and handed to the judge; the measurement changes nothing in the system.
the runs
Each side ran the request twice with a 600-second budget, without and with the notes; the replay and the table use the runs with notes, cut at 200 seconds.
